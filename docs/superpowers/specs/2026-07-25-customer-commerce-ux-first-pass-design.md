# 고객 커머스 UX 1차 완성 설계

작성: 2026-07-25
대상: OMS 사용자 화면(상품 탐색 → 장바구니 → 주문 → 백오더 확인 → 취소)

## 1. 목표

관리자용 OMS/WMS 기능에 비해 약한 고객 화면을, 아래 한 문장으로 시연 가능한 수준까지 완성한다.

> 고객이 상품을 찾아 주문하고, 재고가 없으면 입고 대기 사유와 이후 진행 상태를 이해하며, 자신의 주문을 다시 확인하거나 취소할 수 있다.

새 프런트엔드 프레임워크나 커머스 부가기능을 추가하지 않는다. 기존 Thymeleaf, Spring MVC, Bootstrap 자산과 현재 도메인 상태를 그대로 사용한다.

## 2. 현재 문제

### 사용자 흐름

- 주문 성공 후 생성된 주문 ID를 버리고 `/main`으로 이동해 완료 여부와 다음 행동이 불명확하다.
- 상품 목록과 내 주문이 한 화면의 탭으로 섞여 URL·브라우저 뒤로가기·모바일 탐색이 어색하다.
- 주문 상태가 `ORDER`, `BACKORDERED`, `CANCEL`, `READY`, `COMP` 그대로 노출된다.
- 백오더가 핵심 기능인데 상품 카드의 짧은 문구와 주문 상세 배지 외에는 진행 과정이 보이지 않는다.
- 상품 상세 화면이 없어 검색 결과에서 바로 수량을 정하고 주문해야 한다.

### UI 구조

- `main.html`, `cart.html`, `orderdetail.html`, `orderview.html`이 헤더·버튼·색상·다크 모드 CSS를 각각 가지고 있다.
- 페이지 최대 폭이 760px/1080px로 다르고 성공·오류 메시지 표현도 화면별로 다르다.
- `main.html` 한 파일이 상품·주문·관리자 탭과 JavaScript까지 담당해 583줄이다.

## 3. 설계 원칙

1. **OMS 차별점 우선**: 일반 쇼핑몰 기능 수보다 백오더 상태 설명과 주문 추적을 선명하게 만든다.
2. **서버 렌더링 유지**: 화면 전환은 고유 URL과 표준 GET/POST를 사용한다. 기존 장바구니 수량 조작만 JavaScript를 유지한다.
3. **도메인 변경 최소화**: 새 주문 상태, 결제 상태, 배송 추적 데이터를 만들지 않는다.
4. **모바일 우선**: 640px 이하에서 표는 카드형으로 접히고 주요 행동 버튼은 전체 폭을 사용한다.
5. **접근성 기본 준수**: 상태를 색상만으로 구분하지 않고 텍스트를 병기하며, 키보드 포커스와 오류 `role="alert"`를 제공한다.

## 4. 정보 구조와 URL

| URL | 화면 | 책임 |
|---|---|---|
| `GET /main` | 상품 목록 | 검색·페이징·상품 카드 |
| `GET /products/{id}` | 상품 상세 | 가격·가용 상태·백오더 정책·수량 선택 |
| `GET /cart` | 장바구니 | 선택·수량 변경·삭제·주문서 이동 |
| `POST /orders/checkout-form` | 주문서 | 주문자·배송지·상품·최종 금액 확인 |
| `POST /orders/checkout` | 주문 생성 | 성공 시 생성 주문 상세로 PRG 리다이렉트 |
| `GET /orders` | 내 주문 | 최신순 목록·상태 설명·상세 이동 |
| `GET /orders/{id}` | 주문 상세 | 상태 타임라인·상품·배송지·취소 |

`GET /orders/me`와 `/api/orders/me` 기반 새로고침 UI는 제거한다. 별도 `/orders` 서버 렌더링 화면으로 같은 기능을 더 단순하게 제공한다. API는 외부 사용처가 없음을 확인한 뒤 삭제한다.

## 5. 공통 UI

### 공통 자산

- `static/css/app.css`: 색상 토큰, 레이아웃, 버튼, 폼, 카드, 상태 배지, flash, 빈 상태, 반응형 규칙
- `templates/fragments/layout.html`: 헤더, 전역 내비게이션, flash

내비게이션:

```text
그니마켓 | 상품 | 장바구니 | 내 주문 | (관리자만) 운영 관리 | 로그아웃
```

공통 상태 표현:

| 시스템 값 | 고객 문구 | 보조 설명 |
|---|---|---|
| `ORDER` | 재고 확보 | 상품이 확보되어 배송을 준비합니다 |
| `BACKORDERED` | 입고 대기 | 입고되는 순서대로 자동 배정됩니다 |
| `CANCEL` | 주문 취소 | 고객 요청으로 취소되었습니다 |
| `READY` | 배송 준비 | 아직 배송 완료 전입니다 |
| `COMP` | 배송 완료 | 출고가 완료되었습니다 |

## 6. 화면별 설계

### 6.1 상품 목록

- 상단: 페이지 제목, 검색창, 검색 결과 수
- 카드: 상품명, 가격, 재고 상태, 백오더 안내, `상세 보기`
- 빠른 장바구니 담기는 유지하되 주문은 상품 상세를 기본 진입점으로 둔다.
- 결과 없음: 검색어와 함께 “조건에 맞는 상품이 없습니다” 및 전체 상품 보기 제공
- WMS 조회 장애로 수량을 0으로 폴백한 경우 실제 품절로 오해하지 않도록 “재고 확인 중”을 구분하는 것은 별도 상태가 없으므로 이번 단계에서는 보류한다.

### 6.2 상품 상세

현재 상품 모델의 `id`, `name`, `price`와 WMS 가용수량만 사용한다. 설명·카테고리·리뷰를 위해 DB 컬럼을 추가하지 않는다.

- 상품명·가격
- 현재 가용 상태
- 수량 선택
- 장바구니 / 바로 주문
- 백오더일 때:

```text
현재 바로 출고 가능한 재고가 없습니다.
주문은 정상 접수되며, 입고 후 주문 순서대로 재고가 자동 배정됩니다.
```

상품 이미지는 기존 자산을 재사용한 공통 플레이스홀더로 시작한다. 실제 상품 이미지 세트는 포트폴리오 캡처 품질이 부족할 때만 별도 추가한다.

### 6.3 장바구니

기존 선택 주문·수량 변경·선택 삭제 동작은 유지한다.

- 공통 헤더 적용
- 빈 장바구니 전용 화면과 `상품 보러 가기`
- 모바일에서 상품 행을 카드로 전환
- 선택 합계와 `선택 상품 주문하기`를 하단 고정 요약 영역으로 명확히 표현
- 요청 실패 시 `alert()` 대신 행 또는 상단 flash 영역에 메시지 표시

### 6.4 주문서

현재 검증과 선택 주문 로직은 유지한다.

- 단계 표시: `장바구니 → 주문서 작성 → 주문 완료`
- 주문자, 배송지, 상품, 금액 순으로 단순화
- 백오더 가능 상품이 포함될 수 있음을 주문 버튼 위에 안내
- “총 결제금액”은 실제 결제가 없으므로 **“총 주문금액”**으로 변경
- 결제수단 영역이 실제 동작하지 않는다면 제거한다.

### 6.5 주문 성공

별도 성공 엔티티나 페이지를 만들지 않는다.

`OrderService.order*()`가 반환한 주문 ID를 컨트롤러가 받아:

```text
redirect:/orders/{id}?created=true
```

주문 상세 상단에 1회성 성공 메시지를 표시한다.

- `ORDER`: “주문이 완료되었고 재고가 확보되었습니다.”
- `BACKORDERED`: “주문이 접수되었습니다. 현재 입고를 기다리고 있습니다.”

PRG를 유지하므로 새로고침으로 주문이 중복 생성되지 않는다.

### 6.6 내 주문

- 최신 주문부터 카드 또는 모바일 대응 표로 표시
- 주문번호, 주문일, 총액, 고객용 상태 문구
- 빈 상태: “아직 주문이 없습니다”와 상품 보기 링크
- 검색·상태 필터는 주문 수가 적은 포트폴리오 1차 범위에서는 제거한다.

### 6.7 주문 상세와 타임라인

현재 데이터를 넘지 않는 3단계 타임라인만 표시한다.

| 주문 상태 | 주문 접수 | 재고 확보 | 배송 완료 |
|---|---:|---:|---:|
| `BACKORDERED` | 완료 | 현재 대기 | 대기 |
| `ORDER` + `READY` | 완료 | 완료 | 대기 |
| `ORDER` + `COMP` | 완료 | 완료 | 완료 |
| `CANCEL` | 취소됨 | 중단 | 중단 |

`BACKORDERED`에서는 “입고 시 자동으로 다음 단계로 이동하며 다시 주문할 필요가 없습니다”를 표시한다.

취소 버튼:

- 기존 `cancelable` 규칙 유지
- 확인 문구에 취소 결과를 명시
- 성공/실패는 공통 flash로 표현

## 7. 서버 측 변경

### 필요한 변경

- `ProductService`: 단건 상품과 가용수량을 합친 조회 메서드 1개
- 상품 상세 GET 컨트롤러 1개
- `OrderController.checkout`: 생성된 주문 ID를 받아 상세로 리다이렉트
- `OrderController`: `GET /orders` 추가
- 주문 DTO: 고객용 상태 문구와 대표 상품명이 실제 화면에 필요할 때만 최소 필드 추가
- 공통 fragment 및 CSS

### 바꾸지 않는 것

- 주문·예약·백오더 도메인 규칙
- OMS↔WMS 포트와 REST 통신
- DB 스키마
- 인증/권한 규칙
- 관리자 화면의 기능

## 8. 구현 순서와 검증

### Phase A — 공통 UI 기반

1. 공통 CSS와 header/flash fragment 작성
2. `main`, `cart`, `orderdetail`, `orderview`에 적용
3. 기존 인라인 CSS 중 공통 규칙만 제거

검증:

- 네 화면에서 동일한 헤더·버튼·flash가 렌더링된다.
- 375px와 1280px 폭에서 가로 스크롤이 없다.
- 기존 MVC 테스트와 전체 테스트가 통과한다.

### Phase B — 주문 완료와 내 주문

1. 주문 생성 후 `/orders/{id}`로 리다이렉트
2. `GET /orders` 서버 렌더링 화면 추가
3. 영문 enum을 고객 문구로 교체
4. 주문 상세 타임라인 추가

검증:

- 단건 주문과 장바구니 주문 모두 생성된 주문 상세로 이동한다.
- 정상 주문과 백오더 주문의 성공 메시지가 다르다.
- 다른 사용자의 주문 상세는 계속 404다.
- 취소 가능 조건은 기존과 동일하다.

### Phase C — 상품 상세와 화면 마감

1. 상품 상세 GET과 템플릿 추가
2. 상품 목록을 탐색 중심으로 정리
3. 장바구니·검색 결과·주문 목록 빈 상태 추가
4. 모바일 카드 레이아웃 마감

검증:

- 재고 있음/없음 상품 모두 상세 진입과 주문서 이동이 가능하다.
- 재고 0 상품도 구매 버튼이 막히지 않고 백오더 안내가 보인다.
- 상품 없음은 404로 처리된다.

## 9. 완료 기준

- 신규 사용자가 별도 설명 없이 상품 탐색부터 주문 상세 확인까지 완료할 수 있다.
- 재고 0 주문이 실패가 아니라 입고 대기 주문이라는 사실을 모든 관련 화면에서 이해할 수 있다.
- 주문 생성 후 결과가 즉시 보이며 내 주문 URL로 다시 접근할 수 있다.
- 사용자 화면의 헤더·색상·상태·오류·빈 화면이 일관된다.
- 데스크톱과 모바일에서 핵심 행동이 가려지지 않는다.
- OMS 전체 테스트가 통과한다.

## 10. 제외

- 결제 PG, 쿠폰, 리뷰, 찜, 추천, 배송사 추적
- 카테고리·상품 옵션·상품 관리 CMS
- 새 JavaScript/CSS 프레임워크
- 이미지 업로드와 이미지 DB 컬럼
- Kafka/RabbitMQ 전환

이 기능들은 현재 OMS의 주문·백오더 서사를 강화하지 않으므로 1차 포트폴리오 이후 실제 요구가 생길 때 추가한다.
