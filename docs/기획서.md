## 1. 배경

프로젝트는 일반적인 학습용 쇼핑몰로 시작했다. 주문·배송·재고 JPA 모델에 Spring Security,
QueryDSL, 장바구니 API를 붙이던 중 다음 질문을 핵심 문제로 선택했다.

> 재고가 부족해도 주문을 접수하고, 입고되면 밀린 주문을 자동으로 충족할 수 있는가?

이 정책은 단순 품절 처리보다 OMS에 가깝다. 재고·예약·발주·입고를 별도 WMS가 소유하게
분리하면서 최종 목표를 **미니 OMS와 WMS의 주문 이행 통신**으로 정했다.

## 2. 핵심 정책

```text
가용 재고 = 실물 재고(onHandQty) - 예약(reservedQty)
```

- 주문 시 실물을 즉시 차감하지 않고 WMS에 예약을 요청한다.
- 모든 주문 품목을 예약할 수 있으면 `ORDER`, 하나라도 부족하면 예약 없이
  `BACKORDERED`로 접수한다.
- `BACKORDERED` 주문은 입고나 재고 증가 후 FIFO로 다시 할당한다.
- 관리자가 출고 처리할 때 WMS가 실물수량과 예약수량을 함께 차감한다.
- 주문 취소 시 확보된 예약을 해제하고, 늘어난 가용분으로 다음 백오더를 재할당한다.

## 3. 시스템 책임

| OMS | WMS |
|---|---|
| 회원·인증·장바구니 | 재고 수량과 원장 |
| 상품 카탈로그·판매가격 | 주문별 예약 원장 |
| 주문·백오더 상태와 FIFO 정책 | 보충 요청 원본 |
| 고객 주문 조회·취소 | 발주·부분입고·발주 취소 |
| 재고 조회·보충 요청·출고 지시 | 수동 재고 조정·출고 실연산 |

재고 수량의 정본은 WMS 한 곳이다. OMS DB에는 재고·예약·발주 테이블이 없으며,
필요한 수량을 WMS에 실시간 조회한다. 두 시스템의 상태는 `orderId`로 연결되지만
OMS 주문상태와 WMS 예약상태는 각각 독립된 장부다.

## 4. 통신 채널

| 채널 | 방향 | 역할 |
|---|---|---|
| S1 | OMS -> WMS | 상품별 가용수량 조회 |
| S2 | OMS -> WMS | `orderId` 기반 예약·출고·해제 |
| S3 | WMS -> OMS | 재고 증가 통지와 백오더 재할당 |
| S4 | 양방향 | 타임아웃·재시도·best-effort 통지·보상 스윕 |

- OMS -> WMS `/api/**`는 서비스 계정 HTTP Basic을 사용한다.
- WMS -> OMS `/api/replenishments`도 전용 Basic 자격증명을 사용한다.
- 예약 요청은 WMS의 `orderId` 유니크 원장으로 멱등 처리한다.
- WMS가 응답하지 않으면 신규 주문은 실패시키지 않고 백오더로 접수한다.
- 콜백이 유실되면 OMS의 기본 60초 보상 스윕이 다시 할당한다.

## 5. 대표 시나리오

### 백오더 보충

```text
고객 주문
  -> WMS 예약 부족
  -> OMS BACKORDERED 접수
  -> OMS 관리자가 보충 요청
  -> WMS 관리자가 승인하고 발주 생성
  -> 부분입고 또는 전량입고
  -> WMS 재고 증가 통지
  -> OMS FIFO 재할당
  -> 예약 성공 시 ORDER 승격
  -> OMS 관리자가 출고 처리
  -> WMS SHIP 원장 기록
```

부분입고만으로 주문 전체를 확보할 수 있으면 전량입고 전에도 주문은 승격될 수 있다.
연결된 보충 요청은 발주 전량이 입고돼야 `FULFILLED`가 된다.

### 장애 복구

- WMS 중단 중 주문: 백오더로 접수한 뒤 WMS 복구 후 스윕으로 승격한다.
- OMS 중단 중 입고: WMS 입고는 성공하고, OMS 재기동 후 스윕이 누락 콜백을 회수한다.
- WMS 중단 중 취소·출고: OMS 트랜잭션을 롤백하고 사용자에게 재시도를 안내한다.

## 7. 현재 운영 기능

- 고객: 상품 검색·상세, 장바구니, 선택 주문, 주문 목록·상세·취소, 배송완료 주문 반품 신청·조회
- OMS 관리자: WMS 재고현황, 백오더 수량 분해, 보충 요청, 주문상품 확인,
  단건·선택 일괄 출고
- WMS 운영자: 재고 조정, 부분입고, 재고·예약·원장 조회
- WMS 관리자: 보충 요청 승인·반려, 발주 생성·부분입고·취소
- 공통: 한글 상태표시, 역할 기반 접근제어, 장애 폴백과 백오더·RMA 보상 스윕
- 화면: 고객·OMS 관리자 전체 흐름을 375px 모바일부터 데스크톱까지 지원

## 8. 비범위

- 결제 PG, 쿠폰, 리뷰, 추천, 상품관리 CMS
- 실제 배송사 연동과 배송완료 추적
- 부분출고, 백오더 우선순위·타임아웃 정책
- 교환, 결제 환불, 재고 실사, 안전재고 자동발주, 위치·다중창고
- Kafka/RabbitMQ 전환

OMS V2는 배송 상태를 `READY → SHIPPED → DELIVERED`로 구분하며, 기존 `COMP` 데이터는
같은 의미의 `SHIPPED`로 변환한다. 실제 배송사 연동과 자동 배송완료 추적은 이후 범위다.

## 9. 의도된 한계

- 백오더는 전부-아니면-실패 정책이다.
- FIFO에서 앞선 대량 주문을 충족하지 못하면 뒤의 소량 주문도 기다리는 부분 기아가 생길 수 있다.
- 포트폴리오 1차에서는 정책을 단순하게 유지하고, 실제 요구가 생길 때 부분할당이나 우선순위를 추가한다.
